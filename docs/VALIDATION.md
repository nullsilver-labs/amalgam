# Hosting and access validation

Local validation of the hosting-policy, session and token work, 2026-09-07. No paid API calls, no real account credentials, and no change to the running amalgam or corpus stacks. Everything below was run against the disposable `amalgam-check` project, which was destroyed afterwards.

- `npm run check`: 4306 files, zero errors and zero warnings.
- `npm test`: 51 unit cases across `tests/core.test.ts` and `tests/hosting.test.ts` — the hosting policy in all three modes, ORIGIN validation, the opt-in read as a word rather than any non-empty string, loopback as an address range, IPv4/IPv6/mapped-IPv6 parsing and rejection of malformed addresses, CIDR matching including partial-byte prefixes, forwarded headers honoured only from a trusted peer, secret generation and hashing, the device-label parser, scope and session gates, browser capabilities, plus the existing provider, configuration, context, SSE and Markdown cases.
- `npm run build`: production Node adapter build succeeded.
- Isolated `amalgam-check` stack rebuilt from an empty volume: app, PostgreSQL, mock provider and a Caddy proxy at a pinned `10.89.79.10` on subnet `10.89.79.0/24`, published on `127.0.0.1:18793` with `tls internal`; the app also published on `127.0.0.1:18790`. All four containers healthy.
- `npm run test:e2e`: 6 browser cases, all through the TLS proxy. New coverage: a direct request on 18790 with the canonical `Host` passes; the same peer sending `Host: evil.example` with a forged `X-Forwarded-Host` is refused, because it is not a trusted peer; the session cookie is `HttpOnly`, `SameSite=Strict` and `Secure`; the unauthenticated `/login` shell contains neither the password nor any token; a `read` token lists conversations but gets 403 on `POST /api/chat`, `GET /api/settings`, `POST /api/tokens`, `GET /api/sessions` and `POST /api/logout`; a revoked token gets 401; a bearer token presented to `/api/login` without the password gets 401 and no cookie; Settings › Access reports the secure context, lists both devices from two browser contexts, creates a token whose secret is shown once and starts with `amg_`, revokes it, and signs the other browser out — which lands that browser on `/login` on its next request. Streaming, stop, project instructions, search, export, XSS defence and the mobile layout all continue to pass through the proxy, so SSE is not buffered.
- Three-mode probe against the built server directly, without Docker: `ORIGIN=http://192.168.1.10:8790` with no opt-in answers 503 with a message naming `AMALGAM_PRIVATE_HTTP` and logs a matching refusal; the same origin with `AMALGAM_PRIVATE_HTTP=true` serves normally and logs exactly one startup WARNING about unencrypted traffic and the absent secure context; `ORIGIN=http://localhost:8790` needs no opt-in.
- Migration idempotency: the app container was restarted against an existing database. `schema.sql` ran again without error, `schema_version` holds 1 and 2, and live sessions survived.
- Password rotation: a second app container was started against the same database with a different `APP_PASSWORD`. It logged `APP_PASSWORD changed: 3 signed-in device(s) signed out`, live sessions dropped to zero, and a previously working cookie then received 401 — so the README's promise still holds now that sessions are rows.
- Every compose combination validates with `docker compose … config --quiet`: base alone; base + test; base + corpus; base + inference; base + corpus + inference; base + private (with `AMALGAM_BIND_ADDRESS` set); base + proxied (with `ORIGIN` and `AMALGAM_TRUSTED_PROXIES` set). The corpus overlay joins only the app, to `nullsilver-apps`, never `corpus_default`; the database stays on its internal network in every merge.
- Disposable `amalgam-check` containers, networks and volumes removed afterwards. The real amalgam and corpus stacks were not rebuilt, restarted or reconfigured.

Limitations: mock-backed inference only. The proxy exercised is Caddy with a self-signed local CA on loopback, not a public TLS deployment; no real LAN or VPN client was used, and no external reverse proxy was reconfigured. The corpus connector does not exist, so nothing about corpus authentication was exercised beyond configuration validation. Not an independent security audit.

# corpus connector validation

Local validation of the read-only corpus connector, 2026-09-07. No paid API calls, no real account credentials, no real corpus library, and no change to the running amalgam or corpus stacks — the real corpus was never contacted, started, stopped or reconfigured. Everything below ran against the disposable `amalgam-check` project, which was destroyed afterwards.

- `npm run check`: 4315 files, zero errors and zero warnings.
- `npm test`: 79 unit cases across `tests/core.test.ts`, `tests/hosting.test.ts` and the new `tests/corpus.test.ts` — `classify` over every state (200/204, 401, 403, 421, 429, 404, 500, a refused connection, a timeout, an abort, and `undefined`), and the negative form of the same claim: a 401, 403, 421 or 429 is never reported as `unreachable`, and a 401 or 403 is never reported as `ok`; `corpusConfig` needing both an address and a token, rejecting a non-HTTP one, and showing a host and port rather than a credential; the connector presenting a bearer, calling only the route it means to, copying out a fixed set of hit fields (an invented `internal_path` and the token itself are both absent from the result), refusing to follow a redirect, making no request at all when unconfigured, telling a missing card apart from a broken connector, treating a body that is still indexing as absent text, refusing a `javascript:` link and a non-JSON answer; the `sources` schema on the chat body accepting up to five ids and refusing a sixth, a path, a URL, a query string, a space, an empty string, a 65-character id and a non-array; source injection putting the excerpts before the user's words with the quoted-data framing, numbering them in the order listed, omitting an absent URI, cutting a long body at 6,000 characters, holding the block to half the budget while dropping the last-listed card first, keeping the first card cut down when nothing fits, and reporting an unparseable date as it stands; and `isLocalDestination` over loopback, `host.docker.internal`, RFC1918 and `fc00::/7` literals, bare service names, an empty destination, and the remote side — public hosts and `.internal`, `.local` and `.test` names, which a suffix does not make local.
- `npm run build`: production Node adapter build succeeded.
- Isolated `amalgam-check` stack rebuilt from empty volumes: app, PostgreSQL, the mock provider (also aliased `api.example-cloud.test`, so one model slot looks local and another remote), a new `mock-corpus` fixture on 8892, and the Caddy proxy at the pinned `10.89.79.10`. All five containers healthy. `schema_version` holds 1, 2 and 3, and `messages.sources` is a `jsonb` column.
- `npm run test:e2e`: 10 browser cases, all through the TLS proxy, all passing. New coverage: Settings › corpus shows the endpoint `mock-corpus:8892`, the state `Connected` and the sentence behind it, and "Check now" asks again; a card searched for, attached, sent, and echoed back by the mock provider — proving the excerpt reached the model — with the stored user message still reading exactly what was typed, the attribution `[1] Kestrels of the northbound verge` beneath it, no link because `CORPUS_PUBLIC_URL` is unset, the composer emptied of its chips, "What the model sees" listing the source and its size, and both the reply and the attribution surviving a reload; the disclosure line absent for the model served at `mock` and present, naming `api.example-cloud.test`, for the same container reached at a name with dots in it, and disappearing again when the source is removed; and `/api/integrations/corpus/search` and `/api/integrations/corpus` answering a `read` bearer token — with no `crp_` prefix and no upstream `provenance` field anywhere in the response — and refusing a `write`-only one with 403.

# Model discovery release validation

2026-09-07:

- `npm run check && npm test && npm run build` passed in a secret-free source snapshot: no Svelte errors/warnings, 125 tests across six files, production build successful. All 16 discovery implementation files were byte-compared with the working checkout before release.
- Discovery tests use mocked catalogs and cover authentication, redirect refusal, timeout/body/count bounds, cache invalidation and deduplication, explicit overrides, and bootstrap/chat selection consistency. Ten state/rendered-UI regressions cover missing selections, blocked send paths, explicit replacement, recovery, conversation history and per-tab persistence.

Compose used `--env-file /dev/null`, explicit test-only settings, and the test overlay's empty `env_file`; no production credential reached the fixtures. The test containers, networks and volumes were removed afterwards.
- The GitHub Actions failure caused by expecting `.67` while parsing `192.168.1.10` was corrected in the test, not in the parser. Lowercase corpus Settings text has an explicit browser assertion.

Limitations: discovery endpoints and selection-failure scenarios are mock-backed/state-rendered tests, not a live-provider browser exercise. A listed model does not prove text-chat compatibility or generation permission; discovered context windows remain unknown. No paid inference was used in validation. Not a security audit.
